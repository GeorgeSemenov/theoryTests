# Prefetch, dns-prefetch, preload, preconnect, prerender
[Статья](https://habr.com/ru/articles/445264/)

Чем отличаются следующие атрибуты тэга link ?
```html
<link rel="prefetch" href="???" as="???"/>
<link rel="preload" href="???" as="???"/>
<link rel="preconnect"/>
<link rel="dns-prefetch"/>
<link rel="prerender"/>
```

> Учти, что если у тэга link не указан аттрибут rel с корректным значением, то браузер его проигнорирует
> Запись <link href="image"/> -  не подгрузит заранее картинку, эта запись будет проигнарированна, потому что не указанно корректное значение для rel

> <link rel="stylesheet" href="main.css" as="style" /> - не блокирует парсинг html но блокирует рендеринг, это значит что парсинг продолжится после link запрос и получение стилей будет параллельным, однако рендер страницы будет ожидать применения этих стилей, поэтому отображение странички задержится.

> <link rel="***" href="***" as="!!!" /> - По возможности, указывай аттрибут as - Так браузер сможет определиться с очерёдностью загрузки данных. Значения для as: 
> - `style` для таблиц стилей,  
> - `script` для скриптов,  
> - `font` для шрифтов,  
> - `image` для изображений,  
> - `fetch` для ресурсов, загруженных с помощью `fetch()` или `XMLHttpRequest`,
## PRELOAD 
**Preload** - используется тогда, когда нужно загрузить ресурс (картинку, шрифт, таблицу стилей и т.д.) сиюминутно. Ресурс просто кэшируется (скрипты не выполняются, стили не применяются, просто лежат и ждут, когда пригодятся)

```html
<head>
<link rel = "preload" href="big-img" as="image"/>
...
</head>
<body>
...
<img href="big-img"/>
</body>
```
В данном примере мы заранее просим подгрузить большую картинку big-img асихнронно, чтобы , когда пользователь дошёл до самого тэга img картинка уже была бы в кэше и пользователь увидел бы её сразу.

Не злоупотребляй preload, если загружать всё подряд с preload, то никакого ускорения не будет, потому что у всех будет наивысший приоритет.

Данный тег обязателен, браузер его выполнит в любом случае.
## PREFETCH
**Prefetch** - очень похож на preload, тоже подгружает ресурс и кэширует его, но при этом имеет пониженный приоритет (preload имеет высокий приоритет, поэтому с помощью него подгружают ресурсы, которые пригодятся сразу). Поэтому с помощью prefetch - подгружают ресурсы, которые пригодятся на следующей странице. Например, у тебя есть лендинг с одной ссылкой и 90% пользователей по ней кликают, тогда имеет смысл с помощью prefetch загрузить стили и страницы для следующей страницы (куда ведёт эта ссылка)

```html
<head>
<link rel = "prefetch" href="nextStep.css" as="style"/>
...
</head>
<body>
...
<a href="nextStep.html"> перейти на следующий шаг</a>
</body>
```
Этот тег можно использовать безопасно в любом объеме, он имеет наименьший приоритет и не помешает загрузке никаких ресурсов, однако, стоит учитывать, что будет тратиться трафик пользователя.

Данный тег НЕ обязателен, браузер может его проигнорировать, например, при медленном соединении.

## PRECONNECT
**Preconnect** - используется для предварительного соединения с другим доменом (TCP ? его используют для http запросов) например, ты не знаешь, какой файл стилей тебе нужно будет подгрузить с домена api.my-app.com, но ты можешь заранее установить с ним соединение и когда потребность в стилях возникнет запрос будет мгновенным. Установка соединения занимает десятые доли секунды, это достаточно приличное время.

> Соединение подразумевает:
> 1) резолвинг ip адреса (клиент обращается к DNS чтобы получить ip)
> 2) Установка TCP соединения (клиент - сервер - клиент) или TLS для https, происходит обмен секретными ключами (клиент - сервер - клиент - сервер - клиент)

```html
<link rel= "preconnect" href="https://api.my-app.com" />
```

Не злоупотреблять! Установка соединения - дорогостоящая операция , не стоит ставить более 5 предварительных соединений.

Данный тег не является обязательным, если соединений и так выстроено очень много, то браузер может проигнорировать этот тег.

## DNS-PREFETCH
**DNS-prefetch** - позволяет заранее зарезолвить ip адрес домена к которому будет происходить обращение (например для загрузки какого-либо ресурса) посредством обращения к DNS. Резолвинг для каждого домена требуется лишь единожды.

```html
<link rel="dns-prefetch" href="new-domain.com" />
```

Резолвинг занимает от 20 до 120 мсек.

Данный тег не является обязательным, браузер может его проигнорировать.

> DNS - Domain Name System - переводит человекочитаемое имя сайта (my-app) в уникальный ip адрес (111.222.233.144)


## PRERENDER
**Prerender** - производит рендер указанного ресурса на невидимой вкладке, когда пользователь переходит на этот ресурс, то он загружается мгновенно.

```html
<link rel="prerender" href="steps/nextStp" />
```

Процедура очень дорогая, поэтому использовать стоит только при высокой степени уверенности, что пользователь перейдёт по этому пути.

Тег не обязательный, может быть проигнорирован при нехватке ресурсов (памяти или ещё чего-нибудь)

# Async, defer для script

Чем отличаются эти три записи
```html
<script src="kek" > </script>
<script src="kek" async ></script>
<script src="kek" defer ></script>
```

## Без атрибутов
```html
<script src="kek" > </script>
```
При парсинге (формировании DOM = Document Object Model ) html документа браузер наткнувшись на script - приостановит парсинг, подтянет ресурс указанный в атрибуте src, выполнит скрипт и только после этого продолжит парсинг.

## Async
```html
<script src="kek" async> </script>
```
При парсинге html документа браузер, наткнувшись, на тэг скрипт с аттрибутом async - продолжит парсинг, но параллельно запросит ресурс указанный в атрибуте src, а после того, как ресурс будет скачан - выполнит скрипт, также параллельно с парсингом. Последовательность выполнения скриптов с атрибутом async не упорядочена.

## Defer
```html
<script src="kek" defer > </script>
```
При парсинге html документа браузер, наткнувшиьс на тэг скрипт с аттрибутом defer  - продолжит парсинг, но параллельно запросит ресурс указанный в атрибуте src. После загрузке ресурса - скрипт дождётся оконочания парсинга и выполнит все скрипты с атрибутом defer в том порядке в котором они встречаются в html документе .

# Critical rendering path (процесс рендеринга)
Распишите полностью каждый этап критического пути рендеринга страницы в браузере. Допустим, мы открываем vk.com, какие действия происходят с HTML файлом, который нам пришёл?

## Парсинг - первый этап
Браузер, получив html документ начинает его парсить - создавать DOM (Document Object Model) - это объект html свойствами которого являются тэги завёрнутые в тэг html.
Стоит упомянуть про разные виды поведений:
* Блокирующее поведение: Если при парсинге был встречен тэг, например script(без атрибутов async или defer), то парсинг приостанавливается, пока не подгрузится ресурс, указанный в атрибуте src и не выполнится сам скрипт. Такое поведение называется блокирующим.
* Неблокирующее поведение: Если при парсинге был встречен тэг, например img, то браузер запрашивает картинку указанную в атрибуте src и параллельно продолжает парсинг. Такое поведение называется неблокирующим.

Во время парсинга браузер натыкается на таблицу стилей и строит CSSOM (CSS Object Model) по аналогии с DOM.
Построение CSSOM - не блокирует парсинг, но без построенного CSSOM нельзя перейти к следующему этапу

## Render Tree - второй этап
Когда DOM и CSSOM построены - начинается процесс их объединения, он называется render tree . Теперь у каждого тэга есть свои CSS свойства

## Layout - третий этап
layout - это этап на котором вычисляются размеры блоков, расстояния между ними и ширины границ. 

## Paint - четвёртый этап
При paint'е каждый пиксель получает свой цвет, отсюда и название. 
Если я правильно понял - то для работы с тенями, прозрачностью(opacity) и анимациями(transition) - создаются слои . Слои разделяют отображения на части, чтобы можно было эти части обрабатывать отдельно на CPU и GPU. 

## Composition - пятый этап
Этап при котором объединяются все слои называется composition. В данном случае речь идёт не о слоях, созданных z-index, а о слоях, которыми оперируют в paint, т.е. это просто части единого отображения сайта.

## Display - шестой, заключительный этап
Происходит отображение странички.

# Работа Render Tree , какие элементы участвуют.
Какие элементы DOM-дерева игнорируются при построении Render Tree и не попадают в него? Попадут ли в Render Tree элементы из <head></head>?

Принцип простой - всё что невидимо и не имеет размеров не попадёт в render tree.
Итак в render tree не попадут следующие элементы:
1) C display:none, и все их потомки
2) Все теги в head (потому что не видны и не имеют размеров)
3) скрипты (они тоже не видны и не имеют размеров)

а вот элементы с opacity:0 и visibility:hidden - попадут в render tree, потому что имеют размер, значит для них нужно будет просчитывать геометрию на шаге layout. Хотя эти элементы и не видны.

# Особенности загрузки больших CSS
Браузер получил небольшой HTML-файл, который в себе содержит link'и на 20 мегабайт CSS-файлов. Будет ли отрисован HTML-файл до загрузки этих файлов, или браузер будет ждать их загрузки, и только потом отрисует сайт?

Если CSS подключен через обычные 
```html
<head>
	<link rel="stylesheet">
</head>
```
 браузер будет ждать загрузки и разбора всех этих файлов, и только потом выполнит первую отрисовку страницы.

Объяснение: 
1. **Render-blocking ресурсы**  
    Теги `<link rel="stylesheet">` в `<head>` являются блокирующими рендеринг. Браузер не начнёт отрисовку до тех пор, пока:
     - Не построен DOM (парсинг HTML)
     - **Не построен CSSOM** (объектная модель CSS) — а для этого нужно загрузить и разобрать _все_ указанные CSS-файлы
2. **Почему нельзя отрисовать «частично»?**  
    Браузер не может отрисовать страницу, имея только часть CSSOM, потому что:
      - Неизвестно, какие стили применять к видимым элементам
      - Последующая загрузка CSS может кардинально изменить размеры и позиции элементов, что вызовет дорогой перерасчёт (reflow) и мерцание (FOUC)
3. **Исключения, когда отрисовка _может_ произойти до загрузки CSS:**
    - Если CSS подключён через `<link rel="preload" as="style">` — это загружает файл, но _не применяет_ его до явного `rel="stylesheet"`
    - Если CSS имеет `media` атрибут с условием, которое на момент загрузки не выполняется (например, `media="print"` на десктопе) — такой CSS не блокирует рендеринг
    - Если CSS подключён динамически через JavaScript после события `DOMContentLoaded`
    
Но в условии задачи речь идёт об обычных `rel="stylesheet"` в `<head>` — это классический render-blocking сценарий.

Что означает «блокирует отрисовку до загрузки CSS» на практике:
Пользователь увидит **белый экран** (или пустую страницу) до тех пор, пока не будут загружены и разобраны _все_ 20 мегабайт CSS-файлов. Только после этого браузер выполнит первую отрисовку.

# CORS, от чего защищает.
Что такое CORS? Зачем он был придуман? Он обезопашивает пользователя или сервер?

[Полезная статья по CORS](https://doka.guide/tools/cors/)
CORS- Cross Origin Resource Sharing. Это политика браузера, которая регулирует запросы между разными origin . 

#### Что такое origin:
У каждого сайта есть свой origin, это совокупность домена, протокола и порта (если он указан). Например вот origin: https:\//lol.kek - https это протокол, lol.kek - домен. А вот http:\//lol.kek - это уже другой origin

#### Что такое SOP:
Когда браузер запрашивает html страничку он уже знает origin этой странички. И если вдруг фронт этой странички сделает запрос на другой origin, то браузер его заблокирует, потому что по умолчанию фронт может обращаться только к своему origin (**same-origin-policy** = SOP до 2009 года существовал только он, CORS не было), но CORS расширяет это правило - давай возможность отправлять запросы на разрешённые домены. 

#### Как и где происходит настройка CORS
Настройка CORS должна происходить на сервере через заголовки ответа В браузер его настроить нельзя, браузер просто следует политике полученной от сервера.
Вот заголовок, чтобы указать разрешённый origin - **Access-Control-Allow-Origin**

#### Примеры как защищает CORS
Запросы между разными доменами называются перекрёстными (cross).
Данная политика защищает пользователя.
[Например](https://habr.com/ru/articles/960400/), ты зашёл на сайт, подтянул скрипт, который заглянул в cookie и от твоего имени с информацией, хранящейся в cookie сделал запрос в банк. Если бы не было SOP и CORS, то этот трюк прошёл был и банк провёл транзакцию. Но, благодаря SOP запрос не пройдёт.

Или, если ты открыл две вкладки evil.com и bank.com и теперь evil.com может отправить запрос с твоего компьютера на bank.com маскируясь тобой. Но запрос не пройдёт, потому что CORS его не пропустит.

# Заголовки CORS
Какие есть ограничительные заголовки в CORS? Перечисли все и объясни зачем они нужны

| Заголовок                              | Предназначение                                                                                                                                                                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`Access-Control-Allow-Origin`**      | Указывает, какие origin'ы имеют доступ к ресурсу. Значение `*` разрешает всем, но не работает с `credentials: true`                                                                                                                             |
| **`Access-Control-Allow-Methods`**     | Перечисляет HTTP-методы (GET, POST, PUT, DELETE и др.), которые разрешены при запросах с другого origin                                                                                                                                         |
| **`Access-Control-Allow-Headers`**     | Перечисляет заголовки запроса (кроме простых (см preflight)), которые браузеру разрешено отправлять на сервер                                                                                                                                   |
| **`Access-Control-Expose-Headers`**    | Указывает, какие заголовки _ответа_ (например, `X-Total-Count`, `Custom-Header`) будут доступны JavaScript-коду (через `response.headers.get()`). Без этого заголовка JS видит только простые заголовки (`Cache-Control`, `Content-Type` и др.) |
| **`Access-Control-Allow-Credentials`** | Разрешает (или запрещает) отправку учётных данных (cookies, HTTP-аутентификация) при кросс-доменных запросах. При значении `true` нельзя использовать `*` в `Access-Control-Allow-Origin`                                                       |
| **`Access-Control-Max-Age`**           | Указывает время (в секундах), на которое результат предзапроса (preflight) может быть закеширован браузером, чтобы не отправлять его повторно                                                                                                   |

# Простые запросы CORS 

При каких условиях запрос считается простым в рамках CORS?
Какие content-type поддерживаются в рамках простых запросов?

#### Что делает простой запрос простым.
Простым запросом считается тот запрос, который не провоцирует preflight запросы (см [[#Сложные запросы CORS, как работают, в чём отличие от простых.]]) и удовлетворяет следующим характеристикам:
- Метод: 
	- GET - Запрос на получение информации, 
	- HEAD - запрашивает заголовки, которые приходят в ответ на GET запрос. В общем ответ как на get запрос, но без body
	- POST - Вносит изменения на севере.
- Заголовки: 
	- Все заголовки, которые выставляются user-agent'ом 
	- Accept
	- Accept-Language
	- Content-Language
	- Content-Type но только со значениями (application/x-www-form-urlencoded , multipart/form-data, text/plain)

#### Пример работы политики CORS с простыми запросами:
- Браузер отправляет запрос на север. ВАЖНО - браузер **всегда** отправляет запрос, даже на сторонние origin. Разница лишь в том, что при получении ответа политика CORS может запретить доступ JS к результату запроса. В запросе указывается origin браузера.
```bash
# Пример запроса
GET /data HTTP/1.1
Host: api.example.com
Origin: https://my-site.com
```
- Сервер отвечает (указывает origin, которым позволительна отправка и сразу передаёт запрашиваемые данные)
```bash
HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: https://my-site.com
Access-Control-Allow-Credentials: true

{"data": "secret"}
```
- ПРОВЕРКА на CORS. Браузер считывает заголовок access-control-allow-origin и блокирует обработку запроса если :
	- сервер не отправил заголовок access-control-allow-origin
	- origin и значение заголовка access-controll-allow-origin не совпадают
	- указан флаг access-control-allow-credentials и при этом access-control-allow-origin имеет значение "\*"
- Если блокировка не произошла, то браузер передаёт ответ JS. В противном случае ответ сервера будет сокрыт.

# Сложные запросы CORS, как работают, в чём отличие от простых.

> OPTIONS - http запрос, который запрашивает параметры связи для конкретного URL 
> Используется, чтобы узнать разрешённые методы для запроса, 
> Пример запроса:
```bash
curl -X OPTIONS https://example.org -i
```
>Preflight запросы - это запрос с методом OPTIONS, чтобы убедиться, что сервер использует ли определённые заголовки:  
>Access-Control-Request-Method
>Origin
>Access-Control-Request-Headers

>Идемпотентный метод - это метод, который сколько не применяй результат будет таким же как и при первом применении. Например - замена имени пользователя на Kek. - сколько не применяй имя всегда будет Kek. А вот если метод увеличивает счётчик на 1 то это уже не Идемпотентный метод.

> Разница между методами POST и PUT в том, что PUT - Идемпотентный.

	Сложные CORS запросы отправляются в два этапа. Вначале отправляется preflight запрос(предзапрос), а уже после

#### Что делает запрос сложным.
Сложными запросами считаются запросы с чем-то из следующего списка: 
- методами put или delete (не Get, head, post см. [[#Простые запросы CORS]] ).
- нестандартные заголовки(те которые не указаны в списке [[#Простые запросы CORS]]), например X-API-Key

#### Принцип работы CORS на примере сложного запроса (см. [[#Сложные запросы CORS, как работают, в чём отличие от простых.]])
- До основного запроса браузер производит preflight запрос с OPTIONS, чтобы узнать разрешённые заголовки и методы и разрешённый origin
```bash
OPTIONS /data HTTP/1.1
Host: api.example.com
Origin: https://my-site.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, x-api-key
```
- Сервер отвечает - указывает разрешённые методы и заголовки и разрешённый origin
```bash
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://my-site.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, x-api-key
Access-Control-Max-Age: 86400
Access-Control-Allow-Credentials: true
```
- Браузер блокирует основной запрос если:
	- Не пришёл ответ на preflight запрос
	- Не разрешен какой-либо из заголовков в основном запросе.
	- Не разрешён метод в основном запросе.
	- Выставлен флаг Access-Control-Allow-Credentials в true и Access-Control-Allow-Origin в "\*"
- Если браузер не заблокировал основной запрос, то происходит его отправка с последующей обработкой ответа от сервера и передачей его JS

Немножко исторического экскурса - preflight запросы созданы для того ,чтобы защитить старые серверы (которые работают по настройкам до 2009 года). Такие серверы могут быть уязвимы для сложных запросов и поэтому перед ними отправляются preflight запросы. Старые серверы их не понимают и не отвечают или отвечают с ошибкой, после этого сложный CORS запрос не отправляется.

# Ограничительный заголовки в CORS. Для чего нужные?

Ограничительные заголовки, которые отправляет сервер:
- Access-Control-Allow-Origin : https:\//lol.kek.ru - 
  с какого домена разрешены запросы (если поставить значение * то будут разрешены все запросы, но будет запрещена передача данных для авторизацией см. ниже credential). Браузер, получив такой заголовок с сервера сверяет со своим origin, если они совпадают, то запрос делается.
- Access-Control-Allow-Methods : GET, POST, PUT, Delete, options - 
  какие методы разрешены для запроса клиенту 
- Access-Control-Allow-Headers : Content-type, Authorization ... -
  какие заголовки разрешены в запросах клиенту например Authorization: Bearer \<token>
- Access-Control-Allow-Credentials: true, false -
  Позволяет отправлять http авторизацию и другие учётные данные. Если этот заголовок равен true, то в заголовке Access-Control-Allow-Origin нельзя указать "\*"
- Access-Control-Max-Age: 86400 (24 часа) -
  указывает время в секундах на которое браузер может кешировать результат preflight запроса

Ограничительные заголовки, которые отправляет клиент (браузер):
* Origin: https:\//lol.kek.ru -
  По содержимому этого заголовка сервера понимает разрешён ли доступ.
* Access-Control-Request-Method: DELETE, PUT ... - 
  Клиент запрашивает у сервера - можно ли делать запросы с указанным методом
* Access-Control-Request-Headers: content-type ... - 
  Клиент запрашивает у сервера - можно ли делать запросы с указанным заголовком

# XSS уязвимость, способы защиты.
[статья](https://habr.com/ru/articles/511318/)
> XSS - Cross Site Scripting - процесс размещения вредоносных скриптов на сторонних ресурсах.

#### Чем опасна XSS:
- В некоторых случаях у злоумышленника появляется возможность замаскироваться под пользователя и от его имени производить действия (смена пароля)
- Злоумышленник может незаметно перевести пользователя на клон ресурса визуально почти не отличимый и тогда пользователь может оставить на нём свои данные ,которые попадут злоумышленнику.

#### Способы XSS и способы борьбы с ним:
- Оставить скрипт через input/textarea. Он сохраняется и дальше может быть показан остальным пользователям.  
  Борьба: текстовые вводы нужно экранировать - чувствительные символы \<script> или подобные нужно заменять на аналоги, чтобы браузер не расценил их как JS код. Или можно явно указать браузеру, что данный текст нужно воспринимать только как текст
```js
// ОПАСНО - может выполнить скрипт
element.innerHTML = userInput;
// БЕЗОПАСНО - обрабатывает как текст
element.textContent = userInput;
```
- Вставить скрипт через get параметр. Это хорошо видно по работе поисковиков при вводе запроса - в адресной строке появляется запрос /search?q=kek+puk&oq=kek+puk . Если его ввести самостоятельно в адресную строку, но указать там вредоносный код, то браузер может это съесть и выполнить
  Борьба: Разработать корректный обработчик get запросов, чтобы экранировать символы, которые могут нанести вред.

# CSRF уязвимость, способы защиты.
>CSRF - cross site request forgery - подделка межстайтовых запросов - вид атаки при котором злоумышленник с помощью злодейского сайта или скрипта заставляет браузер жертвы выполнять на доверенном сайте действия от его имени.

#### Принцип атаки CSRF
* Пользователь авторизировался на страничке банка и получил сессионные куки.
* Злоумышленник на своём сайте (evil.com) разметил форму
```html
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="amount" value="1000">
  <input type="hidden" name="to" value="hacker">
</form>
<script>document.forms[0].submit()</script>
```
* Пользователь открыл evil.com и браузер автомотически выполнил отправку зловредной формы на сайт банка, а вместе с этим на сайт банка будут автоматически отправлены все куки, в т.ч. и сессионные, если злоумышленник знает какие запросы писать в банк он может имитировать действия пользователя таким образом, ведь с его запросами будут отправляться сесионые куки.

Куки всегда отправляются со всеми запросами к домену, который эти куки оставил браузеру. Если, конечно это не fetch/XMLHTTPRequest, тогда нужно ещё указать credentails : "include"

#### Способы защиты от CSRF
* CSRF токены - уникальная последовательность псевдослучайных чисел, которая хранится не в куках и отправляется по запросу сервера. Таким образом, даже если злоумышленник имитирует запрос от имени пользователя этот запрос будет без уникального токена и сервер не выполнит такой запрос
* Подтверждение действий пользователя, например на смену пароля или транзакцию. Так как подделка запроса не предоставляет злоумышленнику HTML файл, то и подтвердить действие (нажать на кнопку "да") злоумышленник не сможет.
* Использовать сайт same-site со значениями strict или lax
	* Если same-site = strict то куки будут отправляться с того же сайта с которого они и пришли
	* same-site = lax куки будут отправляться с запросов других сайтов, но только если эти запросы имеют метод get
	* same-site = none - куки будут отправляться всегда



# JWT авторизация

#### Что такое JWT токен
JWT (Jason Web Token) - это обычная закодированная строка, которая разделена на три части с помощью точек. Вот пример
Заголовок.Данные.Сигнатура
**Заголовок** - хранит системную информацию о алгоритма шифрования и другие вспомогательные данные.
**Данные (payload)**- информация, которую мы добавляем самостоятельно, это может быть информация о текущем пользователе (id, userName, roles ...). 
**Сигнатура** - сгенерированная строка с помощью которой можно проверить подлинность JWT токена, чтобы получить данную сигнатуру - нужно получить некий секретный ключ, известный только серверу. Сигнатура создаётся следующим образом: Заголовок + данные шифруется с помощью секретного ключа и получается сигнатура. Таким образом подделать сигнатуру невозможно ,если злоумышленник перехватит токен и внесёт правки, то при шифровке этих данных через секретный ключ - сигнатура изменится и сервер при сравнении  пришедшей сигнатуры и шифрованной поймёт что токен поддельный и отбракует запрос. Поэтому использовать JWT токен для авторизации - безопасно. 

#### Как работает JWT авторизация
JWT токен имеет ограниченное время жизни. Это делается для безопасности, чтобы мошенники не могли постоянно пользоваться  сервисом. 

Как же получить новый токен? Для того, чтобы постоянно не обновлять токен и чтобы процедура получения токена не была утомительной (чтобы не авторизироваться каждые 15 минут(время жизни токена)) решенно было использовать два вида токенов:
ACCESS TOKEN - 
- имеет время  жизни ~ 15-30 минут 
- используется для доступа к приложению. 
- Хранится в localStorage
   
 REFRESH TOKEN
- время жизни ~30-60 дней(если пользователь не входил в приложение 30 дней, то ему придётся заново логиниться, чтобы получить refresh roken) 
- используется для обновления access token'a 
- хранится на стороне клиента в cookies с обязательным флагом httpOnly(чтобы через JS невозможно было эти данные изменить или получить, т.е. эти куки будут установлены только с помощью сервера). Хранится на сервере в базе данных. Получается сессия

#### Почему access токен не защищается также сильно, как refresh токен
Потому что к access токену должен быть доступ у JS, с помощью этого токена производятся разного рода запросы в API 

>Разница между авторизацией и аутентификацией заключается в том, что авторизация это подтверждение того, что ты есть тот, кто ты есть. А аутентификация это проверка на то - достаточно ли у тебя высокая роль для доступа.
  
Схема взаимодействия клиента и сервера при авторизации :
1) пользователь логинится (вводит логин/email и пароль, нажимает кнопку войти, эти данные отправляются на сервер)
2) Сервер производит аутентификацию клиента генерирует пару токенов (refresh и access) и отправляется эти токены клиенту.
3) Токены на стороне клиента сразу сохраняются 
   access token -> localstorage
   refresh token -> cookies (+httpOnly)
4) Теперь клиент считается залогиненным, и для работы с нашим ресурсом он отправляет get запрос, например на отображение личных сообщений.  К запросу в заголовках мы прикрепляем access токен.
5) Сервер проверяет токен, если он не валидный, не поддельный и у него не истёк срок жизни, то сервер обрабатывает данный запрос и возвращает ответ со статусом 200 и данными который запросил клиент.
   Если же токен устарел, то статус ответа будет 401(not authorized)
6) Если клиент получает ответ со статусом 401, то это значит, что токен устарел и сразу отправляет запрос на сервер на обновление access токена используя refresh токен, который установлен в куках.
7) Сервер проверяет refresh токен сравнивая его с тем, который лежит в БД. Если сравнение проходит, то сервер генерирует новую пару access и refresh токенов и отправляет их клиенту (у себя обновляет refresh токен)
8) Клиент обновляет access токен в localStorage и сохраняет refresh токен в кукис(/httpOnly). Всё цикл замкнулся
9) Если клиент не пользовался сервисом долгое время и refresh токен истёк, то клиенту придется заново выполнить вход.

####  Зачем внутрь JWT токена иногда складывают данные пользователя?
Для того, чтобы пройти аутентификацию.

function mergeSort(arr) {
  // Базовый случай: массив из 0 или 1 элемента уже отсортирован
  if (arr.length <= 1) return arr;

  // 1. Делим массив пополам (log n шагов рекурсии)
  const middle = Math.floor(arr.length / 2);
  const left = arr.slice(0, middle);
  const right = arr.slice(middle);

  // 2. Рекурсивно сортируем и сливаем (n операций на каждом уровне)
  return merge(mergeSort(left), mergeSort(right));
}

function merge(left, right) {
  let result = [];
  let leftIndex = 0;
  let rightIndex = 0;

  // Сравниваем элементы из двух половин и добавляем меньший в результат
  while (leftIndex < left.length && rightIndex < right.length) {
    if (left[leftIndex] < right[rightIndex]) {
      result.push(left[leftIndex]);
      leftIndex++;
    } else {
      result.push(right[rightIndex]);
      rightIndex++;
    }
  }

  // Добавляем остатки (если они есть)
  return result.concat(left.slice(leftIndex)).concat(right.slice(rightIndex));
}

const data = [38, 27, 43, 3, 9, 82, 10];
console.log(mergeSort(data)); // [3, 9, 10, 27, 38, 43, 82]

# OAuth авторизация.
Что такое OAuth? Подробно распиши процесс oauth-авторизации. Можно ли совмещать его с JWT авторизацией?

>**Ключевая идея OAuth** — это возможность авторизоваться в одном приложении (клиенте), используя учётную запись из другого сервиса (провайдера), без передачи логина и пароля клиенту. Например, войти на форум (клиент) через Google или GitHub (провайдер).

>OAuth (Open Authorization) - протокол, который позволяет получить ограниченный доступ к вашим данным на другом сервисе, без передачи ваших логина и пароля. Вместо этого приложение получает временный токен, разраешающий выполнять только те действия, на которые вы согласились. Пример работы OAuth протокола - авторизация с помощью гугл аккаунта на каком-нибудь сайте. 

Термины OAuth (ты пытаешься зарегаться на хабре с помощью гугл учётки):
* Resource owner (RO) - это пользователь, который даёт разрешение на использование его данными. (ТЫ)
* Client - приложение, которое запрашивает данные RO (хабр)
* Client id - id клиента, которое используется для идентификации клиента на authorization server.
* Client secret - пароль, который известен только  AS и клиенту и с помощью которого производится конфиденциальный обмен информации.
* Authorization server (AS) - приложение, которое "знает" RO и в котором у RO есть учётная запись, это может быть сервер другой организации, главное, чтобы ему доверял Resource server.(гугл)
* Resource Server (RS) - API или сервис, которым хочет воспользоваться client от имени RO (гугл API)
* Redirect URI (callback URL) - Ссылка по которой authorization server перенаправит RO после того, как client получит разрешения. (хабр просит авторизоваться в гугле и уже после авторизации тебя перенаправляют по этой ссылке, обычно это ссылка на то место, где ты был до этого, допустим на статью, которую ты читал до авторизации)
* Response type - тип информации, которую ожидает получить client, например Authorization code 
* Authorization code - код с небольшим периодом действия, который AS предоставляет клиенту, а клиент потом отправляет client secret и authorization code AS чтобы получить Access Token
* Access Token - ключ, который client будет использовать для связи с resource server'ом от твоего имени.
* Scope - подробное описание разрешений, которые потребуются клиенту, например доступ к данным, или выполнение определённых действий.
* Consent - Authorization server показывает RO Scope и спрашивает - готов ли он дать разрешение клиенту на этот scope.
#### Процесс OAuth авторизации:
1) читаю на хабре(клиенте) статью и решаю авторизоваться, чтобы был видно моё имя сверху в хедере сайта. Нажимаю "Авторизоваться", чтобы хабр получил доступ через гугл к моему имени.
2) Client (хабр) перенаправляет меня (RO) на страницу authorization server(гугл) и включает в запрос clietnID,  callback URL ,  scope и response type
3) Authorization server(гугл) принимает логин и пароль от меня (RO) и авторизирует
4) Authorization server(гугл) выводит consent тем самым показывая, какой scope запрашивает у меня client(хабр). В нашем случае у меня спросят разрешение на передачу моего имени.
5) Если я соглашаюсь с consent то authorization server(гугл) перенаправляет меня с помощью redicret URI (callback URL) обратно на хабр и при перенаправлении передаёт клиенту Authorization code передаёт authorization code , client id, client secret.
6) Authorization server проверяет данные и отвечает access токеном. С этим access токеном клиент может ходить на сервис (гугл) и производить действия.
7. client использует access токен для отправки запроса на resource server с целью получить список контактов.

#### Можно ли совмещать OAuth и JWT авторизацию?
OAuth и JWT **не исключают, а дополняют друг друга**. OAuth решает задачу _как безопасно получить доступ к данным пользователя через стороннего провайдера_, а JWT — _в каком формате передавать информацию об авторизации внутри вашей системы_. Современные приложения часто используют их вместе.

#### Websocket
![[../../../_attachments/Pasted image 20260417123023.png]]

WS соединениt это постоянное двустороннее соединение поверх TCP
Жизненный цикл WS:
1) Рукопожатие
	1) Рукопожатие : клиент отправляет HTTP запрос на сервер, среди заголовков есть передаётся также **sec-websocket-key** который содержит ключ в base64 - формируется особым образом, чтобы его мог понять только сервер, который способен работать с WS. 
	2) Если сервер понимает sec-websocket-key и принимает его, то в ответ будет отправлено сообщение **со статусом 101 (не 200) switching Protocols** и заголовком **sec-websocket-accept** 
	3) Протокол переключён с HTTP на WebSocket
2) Обмен сообщениями
	1) Дюплекс - нет определённой последовательности обмена - сообщения могут быть как от сервера, так и от клиента, их очерёдность не критична.
	2) Сердцебиение (heartbeat) / пингпонг - этот механизм призван проверять актуальность поддержания соединения: сервер с определённым интервалом запрашивает у клиента отправить в ответ серверу запрос. Если запрос приходит, то соединение продлевается, иначе - разрывается
3) Закрытие соединения (closing handshake)
	1) Сторона А - отправляет запрос закрытия 
	2) Сторона Б - принимает запрос закрытия и отправляет запрос подтверждающий закрытие
	3) Сторона А - ждёт ответа-подтверждения закрытия в течении нескольких секунд
	4) websocket соединение переходит в состояние "closed"
4)  Разрыв TCP соединения
	1) освобождаются занятые ресурсы (сокет, память, счётчик подключений)
	2) на клиенте отрабатывает событие socket.onclose()


Особенности: 
* При рукопожатии можно отправить заголовок authorization: bearer, однако для авторизации его использовать нельзя потому что браузерный JS API вебсокета спроектирован так.  Стоит сказать, что authorization сработает на сервере, но в браузере будет проигнорирован.
* Вебсокет не шифрует данные. Шифрование устанавливается при защищённом соединении (wss:// ) (без шифрования будет ws://) до установки соединения websocket - на уровне TCP/TLS
* заголовки отправляются один раз (перед установкой соединения)
* Заголовки sec-websocket-key sec-websocket-accept высчитываются при каждом подключении заново и потому уникальны. Это нужно, чтобы не было возможности закешировать обращение к серверу или от него.
* Крупное сообщение, например потоковое видео может быть разбито на несколько небольших сообщений, первая пачка кадров будет иметь FIN=0 а последняя - FIN=1
* Сервер может общаться с целой сетью клиентов, причём клиент может инициировать у сервера отправку сообщения для других клиентов.

```ts
const myWS = new WebSocket(url, protocols); // создание управляющего объекта
console.log(myWS.readyState);//пока происходит подключение статус будет CONNECTING
console.log(myWS.readyState); // после соединения статус изменится на OPEN
myWS.onopen = function (event) {
	// при установке соединения сразу отправляет сообщение
	myWS.send('Привет, сервер!');
}
myWS.onmessage = (event) => { // при получении сообщения выводим его на экран
	console.log(event.data);
}
myWS.close(); // закрываем соединение
myWS.onclose = (event) => {//При закрытии подчищаем кэш или делаем другие действия
	// ...
};
```

# Polling
Что такое Long Polling? Что такое Short Polling? Зачем они нужны, если есть WebSocket'ы?

[статья](https://habr.com/ru/articles/812693/)

> Short Polling - тип соединения, при котором актуальность данных на сервере проверяется путём отправки запросов с клиента с определённой периодичностью. 
> Самый простой в реализации тип соединения, но самый ресурсотребовательный (сервер постоянно должен отвечать, клиент должен постоянно  прашивать, даже если ничего не поменялось)

Схема работы shrot polling:
* клиент спрашивает сервер (http запрос)
* сервер сразу отвечает клиенту 
* клиент получает ответ 
* клиент ждёт установленное время (пауза)
* цикл повторяется

>Long Polling - тип соединения похожий на short polling, только теперь выжидает сервер. Проще реализуем чем, websocket 

Схема работы long polling:
* клиент спрашивает сервер (http запрос)
* сервер отвечает не сразу, а только если данные на сервере изменились или истёк таймаут
* цикл повторяется

Зачем нужен polling если есть websocket:
- WS нельзя реализовать на старых браузерах или в сетях с ограничениями(корпоративные) 
- Сервер должен поддерживать WS, поллинг же можно настроить на любых серверах.
- WS сложнее в реализации (менджмент, обработка ошибок, расширение), поллинг проще, хотя и боле ресурсотребовательный
- WS избыточен: 
	- если клиенту нужно только получать данные, но не отправлять.
	- Если частота обновления данных на сервере - редкая.

# HTTP
Какие версии HTTP существуют? Перечисли все
Что нового добавилось в HTTP/2? Там было два ключевых нововведения
На основе какого низкоуровневого протокола реализован HTTP/2? А HTTP/3? Чем отличаются эти протоколы?

>HTTP (hyper text transfer protocol) - Набор правил по которым обмениваются информацией браузер и веб-сервера в интернете. По этому протоколу чаще всего получают html страницу. Обычно передаёт данные открытым текстом, для зашифрованного ответа используется протокол HTTPS

[про версии http](https://habr.com/ru/articles/739166/)

Версии HTTP: 0.9, 1.0, 1.1, 2, 3.

В HTTP/2 два главных нововведения: мультиплексирование (много потоков в одном TCP-соединении) и бинарный формат фреймов.

HTTP/2 работает поверх TCP, HTTP/3 — поверх QUIC (который построен на UDP).

Отличие: TCP гарантирует строгий порядок всех пакетов, поэтому потеря одного пакета блокирует все потоки (HOL Blocking). QUIC позволяет потокам быть независимыми — потеря пакета в одном потоке не останавливает другие. Плюс QUIC быстрее устанавливает соединение (1 RTT вместо 2–3) и не рвётся при смене сети.

Дальше идёт не доконца проверенная информация, подправь её, если она будет конфликтовать с предыдущей инфой.

Версии HTTP:  HTTP1, HTTP2, HTTP3 разница между ними лишь в скорости прохождения основных этапов жизни протокола:
* Блокировка соединения: при отправке запроса, который требует длительных вычислений от сервера - канал связи блокируется для отправки других соединений, это необходимо для обеспечения порядка и целостности данных. (TCP гарантирует порядок получения данных) . 
	- HTTP1 : Соединение обрабатывает запросы последовательно, если не получен ответ на первый запрос, то второй не будет отправлен. Если клиентский запрос требует длительных вычеслений от сервера, то канал связи будет пустовать, т.к. необходимо дождаться ответа от сервера. 
	- HTTP2 : Теперь канал удалось разбить на потоки поэтому теперь можно было получать данные по разным потокам, например - CSS, изобржаения, скрипты - всё это загружалось параллельно. Данная версия протокола позволяло не дожидаться ответа на предыдущий запрос и отправлять следующий. Однако, если один из пакетов в каком либо потоке будет потерян - все потоки будут заблокированы до повторной отправки потерянного пакета.
	- HTTP3 : реализован на протоколе QUIC, поверх UDP - обеспечивая тем самым независимые потоки (если в одном потерялся файл, то другие не будут блокированы).
* Время на установление соединения: Перед отправкой запроса клиент и сервер должны договориться о том, как они это будут делать (рукопожатие) - клиент отправляет запрос серверу, а сервер - клиенту. Обычно время установки соединения измеряют в RTT (Round Trip Time) - время полного круга - время за которое сигнал доходит до сервера и обратно.
	* HTTP1 и HTTP2 : 2-3 RTT 
		* Устанавливается TCP соединение = 1RTT
		* Устанавливается защищённое соединение TLS = 1-2 RTT 
	* HTTP 3 : 1 RTT - установка соединения и шифрования объединены в один запрос 
* Объём обязательных данных: каждый запрос требует набора неуникальных заголовков
	* HTTP 1 - заголовки передаются текстом - неудобно и тяжело
	* HTTP 2 - заголовки передаются в бинарном виде, это удобнее
	* HTTP 3 - заголовки сжимаются специальным алгоритмом который позволяет не отправлять повторяющиеся части заголовка, заменяя их на указатели на уже полученные ранее от сервера такие же части.


# DNS
Что такое DNS?
Распиши все этапы резолва ip по домену test.example.domain.ru
Что такое A-запись в контексте DNS? Что такое NS запись?

>DNS (domain name system) - распределённая система преобразующая доменные имена (lol.com) в ip адреса .

Нет единого сервера DNS, данные этой системы хранятся на миллионах серверов, поэтому система является распределённой

Этапы резолва ip адреса по доменому имени test.example.domain.ru:
1) Проверка локального кэша (браузер, приложение, ОС)
2) Если в локальном кэше нет, то Запрос к DNS резолверу, обычно к роутеру или серверу провайдера.
3) Если в кэше резолвера нет, то запрос к корневому серверу 
4) Если в кэше нет, то запрос к NS серверу зоны зоны **ru**
5) Если в кэше резолвера нет, то запрос к NS серверу зоны **domain.ru**
6) -//- example.domain.ru
7) -//- test.example.domain.ru

>А-запись в DNS - связывает доменное имя с ip адресом
``` bash
test.example.domain.ru.  IN  A  192.0.2.10
```
Браузеру нужна именно A-запись, чтобы получить доступ к домену. 
AAAA- запись это аналог A-записи но для ipV6.

>NS запись (name server record) - запись, которая указывает, где хранится официальная информация о домене.
```bash
example.domain.ru.  IN  NS  ns1.example.com.
example.domain.ru.  IN  NS  ns2.example.com.
```
